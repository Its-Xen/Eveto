ADR-0010: Middleware Stack & Ordering Rationale

Date: 2026-9-14 Status: Accepted

Context

FastAPI/Starlette executes middleware using the "Onion Model". The last middleware added is the outermost layer. A request passes down through the layers, hits the route, and the response passes back up through the layers in reverse. Getting this order wrong causes subtle bugs: missing headers in logs, incorrect timing metrics, or CORS failures.
Decision

We define the middleware stack in the following order (Outermost to Innermost):

    RequestIDMiddleware
    TimingMiddleware
    CORSMiddleware
    GZipMiddleware
    API Routes

Rationale

    RequestID (Outermost): Must wrap everything. When it generates the UUID, it binds it to structlog contextvars. If it is outermost, any log generated by the Timing middleware, CORS middleware, or the route itself will automatically include the request_id.
    Timing (Outside CORS/App): Measures the true end-to-end time of the request, including overhead from CORS evaluation and GZip compression.
    CORS (Outside GZip): Must intercept OPTIONS preflight requests and return 204 responses immediately, before the request hits the application logic or GZip.
    GZip (Innermost): Operates strictly on the final response payload. It doesn't care about headers like X-Request-ID; it only compresses the JSON/body.

Consequences

    If we add a new middleware (e.g., an Error Handler), it must be placed carefully. An Error Handler should likely be Outermost (even outside RequestID) to catch lifespan errors, or right inside RequestID to ensure error logs have the ID.
    We accept that GZip compression time is included in our X-Response-Time metric. This is intentional, as we want to measure the total time the client waits.

Under what conditions would this change?

If we implement a Web Application Firewall (WAF) or strict IP filtering, that would become the new outermost layer to drop malicious requests before they even reach our logging or timing logic.
