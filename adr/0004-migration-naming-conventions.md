ADR-0004: Migration and Naming Conventions

Date: 2026-8-27 Status: Accepted
Context

A relational database schema is never static. As Eveto evolves, the database schema must change. We need a reliable, version-controlled way to apply these changes (migrations). Furthermore, because PostgreSQL is case-sensitive and strict about types, we need a consistent naming convention for tables, columns, and constraints to avoid "duplicate object" errors and make raw SQL debugging intuitive.
Options Considered
1. Alembic with Implicit Naming

    What it is: Using Alembic's autogenerate feature and letting SQLAlchemy pick the default names for tables, foreign keys, and constraints.
    Strengths: Fast to write; requires zero configuration.
    Weaknesses: Default constraint names can become long and unwieldy (e.g., fk_events_venue_id_venues); if a database is partially modified manually, implicit names can conflict.

2. Raw SQL Scripts

    What it is: Writing V001__create_users.sql files and running them manually or via a custom script.
    Strengths: Absolute control; easy to read for DBAs.
    Weaknesses: No automatic state tracking; downgrades must be written manually from scratch; no autogeneration from Python models; hard to ensure all environments are in sync.

3. Alembic with Explicit Naming Conventions

    What it is: Using Alembic for version control and migration generation, but configuring SQLAlchemy with a naming_convention dictionary to enforce strict, predictable names for all database objects.
    Strengths: Predictable constraints (e.g., uq_users_email); highly reversible; autogenerates diffs from Python code; native async support.
    Weaknesses: Requires careful manual review of autogenerated files (Alembic cannot detect everything, like Enum type drops); requires a strict naming convention to be enforced across all models.

Decision

We choose Alembic with Explicit Naming Conventions.

We will use Alembic configured for async (asyncpg) to manage schema evolution. All tables will be plural and snake_case (e.g., users, ticket_types). All columns will be snake_case. We will manually verify every autogenerated migration file to ensure explicit drop_type commands are present for PostgreSQL Enums, ensuring true reversibility (downgrade).
Consequences

    Every model change requires a manual migration generation and review step.
    Downgrades are fully supported but must be tested.
    Developers must follow the snake_case/plural convention for all new models.
    We accept that Alembic's autogenerate is imperfect (e.g., it doesn't automatically drop Enums) and requires manual intervention in the migration files.

Under what conditions would this change?

If the project adopted a microservices architecture where schemas were split into multiple databases, we might adopt a tool like Flyway or Liquibase to manage migrations across multiple codebases. If the team grew significantly, we might enforce a stricter migration review policy using CI/CD checks.
